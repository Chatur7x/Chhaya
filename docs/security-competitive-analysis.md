# Chhaya V14 security and product comparison

**Research date:** 26 October 2026
**Scope:** Public protocol/security documentation for Signal, WhatsApp, iMessage, Telegram, Session and Threema, compared with the checked-out Chhaya code and `docs/delivery-checklist.md`.

This is a source-based architecture comparison, not a penetration test, cryptographic proof, speed benchmark or endorsement of any vendor's marketing claims. Competitor features change by version, platform, account settings and rollout. Claims about competitor architecture below link to the vendor's technical or support material. Chhaya claims are limited to what its current source paths and tests demonstrate.

## Summary

Chhaya has a useful privacy direction: account IDs do not require a phone number or email, message bodies are encrypted on-device, and the app requires users to compare or scan a contact identity before opening an encrypted session. That does **not** make it a military-grade or intelligence-agency-grade product.

The shipping direct-message path currently derives an X25519 shared secret from long-term identity keys, initializes Chhaya's own Double Ratchet implementation, and adds a deterministic HKDF epoch key. The `Pqxdh` and ML-KEM code is not called by the live message/session path. There is no live post-quantum prekey publication, signed prekey bundle, PQ ratchet reseeding, or downgrade negotiation. The deterministic SPQR-shaped epoch chain contributes no fresh post-quantum entropy. Therefore Chhaya must not claim post-quantum messaging today.

Chhaya's onion router is not the message transport. Its client seeds a directory with placeholder hostnames and randomly generated public keys; normal messages go through the configured HTTPS API and WebSocket signaling services. The backend stores encrypted message envelopes and can associate account IDs, conversation membership, timing, and delivery activity. Chhaya must not claim onion anonymity or hidden social graphs today.

The strongest competitors' advantage is not a longer algorithm list. They have mature, deployed protocols, established user verification and recovery flows, broader multi-device behavior, years of operational experience, public technical documentation, and in some cases formal analysis, independent audits or transparent key directories. Chhaya's largest security gap is the distance between prototype crypto components and a reviewed, deployed end-to-end protocol.

## Security properties are different layers

- **E2EE** protects content from the delivery server when implemented and authenticated correctly. It does not hide who talks to whom, stop screenshots, secure a compromised phone, or make a bad identity check safe.
- **Forward secrecy (FS)** limits exposure of old messages after a later key compromise. It depends on ratchet state and key deletion working as designed.
- **Post-compromise security (PCS)** lets a session recover after compromise only after fresh secret input unknown to the attacker. A deterministic KDF epoch from an old seed is not fresh secret input.
- **Post-quantum confidentiality** requires standardized PQ key material to be authenticated, negotiated, carried on the wire, consumed and erased correctly. Bundling a KEM library or calling a function in a unit test is not protocol deployment.
- **Metadata privacy** needs separate design. An E2EE server can still observe IP addresses, account IDs, recipients, conversation membership, timing and sizes unless the protocol hides or minimizes them.
- **Device security** includes OS updates, key storage, app lock, memory exposure, screenshots, notification previews, backups, malware and physical access. No messenger can promise safety after a hostile party controls an unlocked endpoint.
- **Availability and speed** depend on regions, network, push delivery, queues, server load, attachments, group size and routing. Protocol complexity alone cannot produce a credible speed ranking.

## Speed comparison: what can and cannot be concluded

No reproducible, same-device/same-network benchmark was found that compares all these apps under equivalent conditions. Chhaya has no published independent latency, delivery, battery or throughput benchmark. A numeric “faster than” claim would be invented.

Architecture suggests trade-offs, not measured outcomes:

1. Chhaya's current message path sends one HTTPS request to its configured backend; the server then stores the envelope and notifies current members. This avoids onion-hop latency in the path that actually runs.
2. Chhaya's three-hop onion code is not wired into that path, so it currently provides no messaging latency or anonymity property.
3. Session's onion/decentralized delivery adds routing and storage hops by design; that can improve origin privacy while increasing latency/availability dependencies. The actual effect must be measured on live deployments.
4. Chhaya group sends prepare one ratchet envelope per recipient, so client work and bytes grow with member count. Mature sender-key/group protocols reduce repeated per-message fan-out costs but introduce group-state and membership-change complexity.
5. WhatsApp, Signal, Apple and Telegram operate mature production infrastructure at large scale. Chhaya has no publicly deployed backend or load data in this project state, so real-world speed cannot be compared.

For a valid Chhaya benchmark, measure cold start, local encrypt/decrypt, enqueue-to-server-ack, recipient receive latency, p50/p95/p99, reconnect delivery, attachment throughput, group sizes 2/8/32, CPU, memory, battery, data volume, and relay-region/network conditions. Publish the build, device, OS, network, server region, sample count and raw test method. Compare competitor apps on the same devices and network only if their terms and measurement can be respected.

## Priority plan to become a credible high-security messenger

### P0 — correct claims before promotion

1. Remove “military-grade”, “CIA/Mossad/RAW level”, active PQ, onion anonymity, decentralized files and coercion-resistance claims unless they are independently proven and deployed. There is no meaningful universal certification called “military grade”.
2. Publish a concise threat model: which attacker, which asset, which platform/version, and explicit exclusions such as compromised endpoints, coercion, traffic analysis and recipient screenshots.
3. Keep `docs/delivery-checklist.md`, product copy and actual app labels consistent. Never label an unverified contact “secure” or a classical session “quantum safe”.

### P1 — make the live protocol reviewable

1. Freeze a versioned protocol specification before adding features. Prefer a maintained, independently reviewed protocol implementation over custom cryptographic composition; if retaining Chhaya's ratchet, commission a qualified protocol review and formal model.
2. Replace static identity-DH setup with a reviewed asynchronous authenticated handshake: signed rotating prekeys, one-time prekeys, replay protection, canonical transcript/identity binding, account/device keys, version negotiation and downgrade resistance.
3. Integrate ML-KEM only through an authenticated wire protocol and known-answer-tested native provider. Add real PQ ratchet reseeding with fresh peer-contributed secrets, deletion rules, out-of-order handling and downgrade tests. Keep PQ disabled and clearly labeled until Android and iOS end-to-end vectors pass.
4. Add key transparency or an independently auditable identity log, key-change alerts and a usable QR/safety-number flow. A user-entered ID is only safe when compared through a trusted channel.
5. Specify group membership-change semantics: who can add/remove, device-level membership, key epochs, history access, sender authentication, removal behavior and state rollback/replay handling. Test concurrent mutations and real multi-device histories.

### P2 — metadata, devices and operations

1. Minimize server-visible social graph and IP data. Document every retained field and retention window. Evaluate sealed-sender-style submission, short-lived queues, privacy-preserving push and independent relay operation.
2. Ship real onion relays only after key authentication, routing protocol review, Sybil/DoS analysis, node diversity, traffic analysis and deployment. Placeholder keys/hostnames must never appear as active network infrastructure.
3. Finish secure device linking/revocation, encrypted cross-platform backups, notification privacy, screen-capture controls with honest OS limits, and account/session recovery. Test restore and revocation on physical Android/iOS devices.
4. Add deployment security: HTTPS/TLS, database backups and restore drills, secret rotation, abuse controls, alerting, incident response, retention/deletion policy and reproducible releases.
5. Commission independent mobile, backend, protocol and privacy reviews. Remediate all critical/high findings, publish the scope and version audited, and retest after fixes.

### P3 — speed and product quality

1. Establish the benchmark suite before optimizing. Measure realistic devices/networks and compare with app-specific baselines.
2. Add resumable encrypted media chunks and per-device delivery; keep resource limits, abuse controls and storage expiry explicit.
3. Complete background call integration, push, multi-device, onboarding, accessibility, localization, crash recovery and lifecycle tests on both platforms.

## Naming and trust

Do not market Chhaya as suitable for intelligence agencies, clandestine operations, military use, or protecting users from state-level targeted attacks. No such deployment, audit, certification, operational infrastructure or incident history is present in this repository. A responsible goal is to build a privacy-focused messenger with clearly bounded, independently tested guarantees and publish the evidence for each release.
